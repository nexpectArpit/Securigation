# System Architecture

# AI Security Investigation Platform

## Purpose

This document defines the high-level architecture of the AI Security Investigation Platform.

It explains how information flows through the system from the moment a user uploads log files until an AI-generated investigation response is returned.

This document intentionally avoids implementation details and focuses on architecture, responsibilities, and component interactions.

---

# Architecture Philosophy

The platform is not a chatbot.

The platform is an Investigation Engine.

The AI model is only one component in a larger investigation pipeline.

The most important architectural principle is that **Paritok is a first-class component**, not an optional optimization.

Every investigation query must pass through Paritok before reaching the LLM.

# Component Responsibilities

## Investigation Manager

Responsible for:

- creating investigations
- managing uploaded files
- storing investigation metadata
- maintaining investigation state
- tracking previous questions

---

## File Upload Service

Responsible for:

- receiving uploaded files
- validating uploads
- handling multiple files
- tracking upload progress
- storing original files safely

The upload service should not perform AI processing.

---

## File Detection Engine

Responsible for identifying the uploaded file format.

Examples include:

- Windows Event Logs
- Apache Logs
- Firewall Logs
- Linux Syslogs
- Authentication Logs

If the format cannot be identified, the system should fall back to generic text parsing whenever possible.

---

## Parser Engine

Responsible for extracting structured information from uploaded files.

The parser should convert raw log entries into normalized security events.

The parser architecture should be modular.

New parsers should be added without changing the rest of the system.

---

## Event Normalization Engine

Different log formats contain different fields.

The normalization layer converts every parsed event into a common investigation model.

Example normalized fields include:

- timestamp
- source
- destination
- hostname
- username
- event type
- severity
- message
- metadata

Every downstream component works only with normalized events.

---

## Investigation Storage

Stores:

- investigations
- uploaded files
- normalized events
- previous questions
- previous answers
- generated timelines

This layer represents the persistent investigation state.

---

## Search & Retrieval Engine

The retrieval engine is responsible for finding only the events relevant to the user's question.

The entire investigation should never be sent directly to the LLM.

Instead:

Question

↓

Retrieve Relevant Events

↓

Return Investigation Context

The retrieval engine should be optimized for structured log searches.

---

## Paritok Layer

This is the core architectural component.

Responsibilities:

- compress retrieved investigation context
- reduce repeated information
- preserve investigation quality
- reduce token usage
- improve response speed

Every AI query must pass through this layer.

The system should expose measurable metrics generated by this stage.

---

## LLM Reasoning Engine

The LLM is responsible only for reasoning.

It should never process the complete investigation directly.

Its responsibilities include:

- answering questions
- summarizing findings
- identifying suspicious activity
- explaining evidence
- generating investigation summaries

The LLM receives only compressed context.

---

## Evidence Generator

Every answer should include supporting evidence.

Evidence should reference the retrieved investigation events.

The platform should avoid unsupported conclusions.

---

## Timeline Generator

Responsible for creating chronological investigation timelines.

The timeline should summarize the progression of important security events.

---

## Metrics Engine

Responsible for visualizing the effectiveness of Paritok.

Metrics include:

- Original Context Size
- Compressed Context Size
- Compression Ratio
- Estimated Token Savings
- Estimated Cost Reduction
- Estimated Latency Reduction

These metrics should be displayed after every investigation query.

---

# Investigation Workflow

1. User creates an investigation.

2. User uploads one or more log files.

3. Files are validated.

4. File types are detected.

5. Appropriate parsers extract events.

6. Events are normalized.

7. Events are stored.

8. User asks a question.

9. Search engine retrieves relevant events.

10. Retrieved context is compressed by Paritok.

11. Compressed context is sent to the LLM.

12. LLM generates an answer.

13. Evidence is attached.

14. Timeline is updated.

15. Paritok metrics are displayed.

---

# Scalability Principles

The architecture should remain modular.

Every major component should be independently replaceable.

Examples:

- Replace Groq with another LLM.
- Add additional log parsers.
- Replace search engine.
- Extend timeline generation.
- Add new investigation features.

These changes should not require redesigning the overall architecture.

---

# Architectural Goals

The architecture should prioritize:

- modularity
- maintainability
- scalability
- explainability
- investigation quality
- efficient large-context reasoning

The architecture should clearly demonstrate that Paritok is a central component of the investigation pipeline rather than an optional enhancement.
